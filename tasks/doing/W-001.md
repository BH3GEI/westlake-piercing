## 1. 墙签名 (wall signature)
uptodown `AppCompatDelegateImpl.createSubDecor()` 对 `R.styleable.AppCompatTheme_windowActionBar` 调 `hasValue()`。目标 APK 的真实 attr 是 `com.uptodown.R.attr.windowActionBar=0x7f040691`；`AppThemeBar(0x7f15000e)` 直接写了 `<item name="windowActionBar">false</item>`。

旧 probe/白板用了 `0x010100b0`，Android SDK 证明它是 `android:autoLink`；framework 的 `android:windowActionBar` 是 `0x010102cd`，也不是 AppCompat styleable 中的 app attr。故旧 `uamHasWab=false` **不是**双包 parent-chain 断链证据。本卡先建立真 oracle，再 A/B 判断 app-only 与 app+framework，不能预设双包是根因。

## 2. 封闭上下文 (self-contained context)

### 当前认识（2026-07-10 oracle audit → 22:48 VLL advance）
- **已核验**：APK `public.xml` 为 `windowActionBar=0x7f040691`、`colorPrimary=0x7f040141`；Android SDK 为 `windowContentOverlay=0x01010059`。probe 两处 attr 数组已按此修正。
- **已核验**：AppCompat 的 styleable index 0x75 指向 `com.uptodown.R.attr.windowActionBar`；`createSubDecor()` 正是检查它。
- **已穿透（22:48 实测）**：`nativeW001Append` 入口从 `ILL` 改为 **`VLL`（void + 两引用参数）**，与 `nativeWriteText` 同 shorty 类，`interpreter.cc:1189` 不再拒派发（日志中该方法 ILL 行 = 0）。native 全程执行，heartbeat 出 `nativeSet=ok ck=2`：framework-res 经四参 `nativeSetApkAssets(...ZZ)V` 真正进入 AssetManager。**oracle 判据 1/3 达成。** 状态只从 native heartbeat 读取（VLL 无返回）。证据：`evidence/W-001/2026-07-10-vll-trampoline-advance.txt`。
- **新前沿墙（本卡当前卡点，2026-07-11 定性到底）**：`new Resources(am,dm,cfg)` 抛 `UnsatisfiedLinkError: No implementation found for boolean android.os.Trace.nativeIsTagEnabled(long) (tried Java_android_os_Trace_nativeIsTagEnabled and ...__J)` → A/B 两腿都停在 `step=res`。**已首次直接抓到该异常**（oracle 现采集 `w001-abAex.txt`），推翻旧「日志里 0 条 UnsatisfiedLink → 也许不是 Trace」的顾虑（旧日志只是没采到 caught sink）。
- **根因确认（observed）**：**boot 级双 `android.os.Trace` mirror::Class**。`nativeW001BindTrace` 实测 `boot=0 amldr=m2 res=m2 same=m1`：FindClass 的 Trace 能绑成功(boot=0)但无济于事；`android.content.res.Resources` 自身 loader 非 null 却 `loadClass("android.os.Trace")` 抛 CNFE(res=m2)；`am` 是 boot-defined(amldr=m2)。`ResourcesImpl.<init>` 对 Trace 的引用由框架 dex 的 `ClassLinker::ResolveType` 解析，得到的类**既 ≠ FindClass 那个,也无法用任何 loader.loadClass 取到** → 「RegisterNatives 按 class 句柄」结构上够不到。
- **下一修法（需顾问+用户授权,均落 ART 内部,卡片 forbidden 明列）**：路 A 让 ART 自动 JNI-link 命中我们导出的 `Java_android_os_Trace_*`（把 sidecar 以 null-classloader 系统库注册,使 `Libraries::FindNativeMethod` 对 boot-loader Trace 命中);路 B 从源头消除双 Trace(阻止 core-libart.jar 经 tolerant-jar 二次加载,改 `local-build-adapters/art-latest` 嵌入运行时装配,不碰 stock framework jar);路 C 够到 dex-resolved Trace 句柄(标准 JNI 不可达)。证据:`evidence/W-001/2026-07-11-trace-dualclass-confirmed.txt`。
- **源码审计（已闭环）**：native append 曾查不存在的三参 `(J,[ApkAssets])V`，现已四参调用成功才写 `nativeSet=ok ck=N`，旧 `ck=2`=array length 的假信号已消除。
