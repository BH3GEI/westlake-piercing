W-001 / 墙#43 — Trace.nativeIsTagEnabled ULE 根因订正（observed，2026-07-11 主号）

本文件订正并取代 evidence/W-001/2026-07-11-trace-dualclass-confirmed.txt 的“boot 级双 Trace class（boot image + tolerant-jar 双载）”结论。
那个结论建立在“-Ximage boot image 生效”的前提上，本班次实测该前提为假。以下全部为板上 5583f5be 实测（observed），非推测。

================================================================
1. 旧根因（dualclass-via-boot-image）已被证伪
================================================================
- launcher `oracle/device/run-utd-w001.sh` 从不设 `WESTLAKE_BOOT_IMAGE`；sidecar 里 `-Ximage`
  仅在 `getenv("WESTLAKE_BOOT_IMAGE")=="1"` 时加入（westlake_..._probe.c 附近 build_image_option 门）。
- 板上 probe 日志 grep：只有 `-Xbootclasspath:...`，无任何 `-Ximage` 行 → **boot image 未生效**。
- 故“core-libart.jar 经 boot image + tolerant-jar 双载”不成立：本 run 只有一条 bootclasspath 装配路径。

================================================================
2. android.os.Trace 的定义分布（dex string-pool 实测）
================================================================
- 唯一定义者 = `framework.jar`（`nativeIsTagEnabled` 符号仅出现在 framework.jar/classes3.dex；
  core-libart.jar / adapter-mainline-stubs.jar / oh-adapter-framework.jar / adapter-runtime-bcp.jar 均无）。
- 但 framework.jar **同时挂在两处**：`-Xbootclasspath`（sidecar build_bootclasspath_option）
  与 app `-cp`（build_classpath_value）。这是本环境唯一的潜在“重复装配”来源（非 boot image）。

================================================================
3. RegisterNatives「成功但没绑上」——决定性实测（bcall）
================================================================
nativeW001BindTrace 里新增 call-test：对 FindClass("android/os/Trace") 得到的 boot_trace
先 RegisterNatives（6 个 Trace native，含 {"nativeIsTagEnabled","(J)Z"}），rc=0（boot=0，无异常），
随后立刻 `CallStaticBooleanMethod(boot_trace, nativeIsTagEnabled, 0L)`：

    trace boot=0 amldr=m2 res=m2 same=m1 syslib=m1 bcall=1        （x3，稳定）

- bcall=1 = 该调用抛 UnsatisfiedLinkError。
- 即：**在我们刚 RegisterNatives 成功的同一个 class 上，调用 nativeIsTagEnabled 仍然 ULE。**
- → 这不是“双 class / 句柄够不到”问题；是 RegisterNatives 报成功但 entry_point_from_jni_ 没有变成我们的 fn。
  （JNI Call* 与解释器 invoke 最终都读 entry_point_from_jni_；两条路都命中 dlsym 存根。）

================================================================
4. PATH A（LoadNativeLibrary 注册 sidecar 进 libraries_）结构性死路
================================================================
sidecar 里用 dlsym 取到导出的 `art::JavaVMExt::LoadNativeLibrary(...)`（GLOBAL DEFAULT，符号在），
按 libc++ SSO/long std::string ABI 传参调用，读回它的 error_msg（长串，size=0x2c=44）：

    lnl=false
    errmsg(long)=Dynamic loading not supported (static build)

- 这是 **musl 静态构建版 dlopen 存根**返回的串。libwestlake_art.so 静态链接了 musl → 它内部的
  dlopen/dlsym 都是死存根。ART 运行时无法 dlopen 任何东西。
- 对照：我们自己在 sidecar 里 `dlopen("/data/local/tmp/w1.so")` = ok（selfdlopen=ok），因为
  sidecar 的 dlopen 运行时绑到板上真正的动态 linker；ART 的 dlopen 绑到它自己静态存根。
- 结论：走公有 API 把 sidecar 注册进 `libraries_` 不可能（dlopen 死）。libraries_ 的自动 JNI-link 也就永远命不中我们的 Java_android_os_Trace_*。

================================================================
5. 解释器侧真相：interpreter.cc 的 ZJ 分支存在，但拿到的是 dlsym 存根
================================================================
`local-build-adapters/art-latest/patches/runtime/interpreter/interpreter.cc`：
- InterpreterJni 是巨型「按 class+shorty 硬派发」表。static 段 L2314 明确有：
      } else if (shorty == "ZJ") {  // boolean fn(JNIEnv*, jclass, long) — Trace.nativeIsTagEnabled
        fn = GetEntryPointFromJni(); result->SetZ(fn(env, klass, arg0));
  → 分支本身是对的；如果 GetEntryPointFromJni() 是我们的 fn，就能通。
- 但 XmlBlock 的邻近分支（L2372/L2427）留了注释与 workaround：GetEntryPointFromJni() 返回的是
  “generic-JNI trampoline / 未解析 dlsym 存根”，不是真 fn；XmlBlock 靠 `FindCodeForNativeMethod`
  重解析（它 special-case 了 XmlBlock，能从真库拿到符号）。Trace 无 special-case → 落普通
  libraries_ 路 → 空 → ULE（消息正是 “tried Java_android_os_Trace_nativeIsTagEnabled and ...__J”）。
- L2473 的 static fall-through 只 LOG(WARNING)+清结果寄存器，不抛 ULE；故 ULE 来自 ZJ 分支里调用 dlsym 存根。

================================================================
6. 净结论 / 下一步（需决策）
================================================================
真墙：Trace.nativeIsTagEnabled 的 native 实现无法被 ART 任何运行时解析路命中——
  (a) RegisterNatives 报成功但没把 entry_point_from_jni_ 变成我们的 fn；
  (b) libraries_ 自动 link 路 + FindCodeForNativeMethod 普通路都靠 ART 自身 dlopen/dlsym，而后者是静态死存根；
  (c) interpreter.cc 有正确 ZJ 分支，但拿到的仍是 dlsym 存根。

可行修法（互斥，均非“双 class 绑句柄”）：
- P1 substrate（非 forbidden，可自己做）：android.os.Trace 是我们的 framework 衬底，不是 stock APK。
  把 isTagEnabled/traceBegin 做成纯 Java no-op（或在 bootclasspath 更靠前的 adapter jar 覆盖 Trace），
  彻底不走 native。风险：需重打 framework dex / 处理其他 Trace 使用者。待 Trace 字节码确认是否有静态字段闸门
  （若有闸门，甚至只需 JNI SetStaticField，最省）。
- P2 ART 内部（forbidden：class_linker，需顾问+用户授权）：用导出的
  `art::ClassLinker::RegisterNative(Thread*, ArtMethod*, const void*)`（符号在，index 13134）
  直接把目标 ArtMethod 的 entry_point_from_jni_ 设成我们的 fn。需拿到框架真正解析的那个 Trace ArtMethod。
- P3 重建 ART（PATH B，治本，暂 blocked：yao 账号无 AOSP-15 ART tree/OHOS SDK）。

7. 追加实测：clinit/init 顺序假说已证伪（bcall2）
================================================================
在 boot_trace 上做了 force-init + 重注册 + 重调用实验：
    trace boot=0 amldr=m2 res=m2 same=m1 syslib=m1 bcall=1 init=0 bcall2=1   （x3 稳定）
- init=0：GetStaticLongField(TRACE_TAG_*) 成功触发 <clinit>，未抛异常 → Trace 静态初始化不调用未绑 native。
- bcall2=1：**force-init 之后再 RegisterNatives，再调用 nativeIsTagEnabled 仍 ULE。**
→ “类未初始化 / clinit 重置 entry point” 假说证伪。RegisterNatives 在 boot_trace 上无论 init 前后都绑不上。

对照关键事实：我们自己 probe 的 nativeW001Append（app 类，VLL）经 RegisterNatives **能**派发（nativeSet=ok 实测）。
唯一差别 = boot/framework 类 vs app 类。
净判断（inferred，基于以上 observed）：**本 ART 的 JNI RegisterNatives 对 boot/framework 类 native 不生效**
（注册后 entry 仍是 generic-JNI dlsym trampoline，正是 interpreter.cc XmlBlock 注释所述），
且 ART 自身 dlopen/dlsym 是静态死存根 → 运行时无任何路能解析 Java_android_os_Trace_nativeIsTagEnabled。

判据不变：#43 仅在 artifact 全匹配 + nativeSet=ok + wabAttr=0x7f040691 + uamHasWab=true 才跃迁。LEDGER #43 维持 🔧。
