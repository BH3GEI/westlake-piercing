TWO ROOT CAUSES FOUND & FIXED (this is why the first two on-device shots read wrong):

1) interposer-R2 (pixel readback returned -1, Java hex8((int)-1)=ffffffff "white"):
   The board's libhwui-adapter had the OLD egl_interposer folded in (NO capture). hwui's
   OWN eglSwapBuffersWithDamageKHR bound to that in-DSO copy (-Bsymbolic-functions), so the
   NEW capturing egl_interposer in the standalone renderer.so was NEVER called by hwui
   (log: center_argb appeared 0 times). g_wl_swap_count stayed 0 -> nativeLastSwapArgb=-1.
   FIX: rebuild libhwui-adapter WITH the new capturing egl_interposer.o folded in (the
   -Bsymbolic-functions self-bind makes hwui call the capturing copy), deploy it as libhwui.so
   FIRST on LD_LIBRARY_PATH so register_hwui_if_present's dlopen("libhwui.so") + the renderer's
   DT_NEEDED libhwui.so BOTH resolve to the single capture instance (R2: one libhwui mapped once).
   The renderer is rebuilt INTERPOSER-FREE (g_wl_last_swap_argb UNDEFINED -> resolved from
   libhwui at runtime) so there is exactly ONE g_wl global, in libhwui. Confirmed after fix:
   log shows center_argb=0xffff0000/0xff00ff00, [wl-capture] drawFB=0 readFB=0 readErr=0x0.

2) #49 @CriticalNative bounds unbound (buffer read 0x00000000 all-zero, panel black):
   Java RenderNode.setPosition() dispatches through @CriticalNative nSetLeftTopRightBottom,
   which is UNBOUND on this imageless ART (device log: "WLXMLIJ3 nSetLeftTopRightBottom
   realfn=0"). The root node kept EMPTY bounds -> hwui clipped the app's drawColor to an empty
   rect: frame0 replayed onDrawPaint #1 (fDAG.size=1) but produced 0 pixels; frame1 computed
   empty damage (fDAG.size=0) and did not even swap -> changed=no. nDrawColor itself is
   @FastNative and IS bound, so the drawColor op was correctly in the display list.
   FIX (render path workaround, not the ART fix): the renderer holds the native RenderNode*,
   so in nativeInit it sets bounds DIRECTLY in C++ (no JNI):
       RenderProperties& props = rootNode->mutateStagingProperties();
       props.setLeftTopRightBottom(0,0,w,h); props.setClipToBounds(false);
       rootNode->setPropertyFieldsDirty(0xFFFFFFFF);
   exactly mirroring the proven pure-C westlake_upscreen_color_smoke. After fix: onDrawPaint
   12x, fDAG.size=1 for all, frames render full-screen red/green, changed=yes.
   NOTE: this is a render-path bypass; the general #49 @CriticalNative publish fix (task #7,
   W-003) is still the proper cure for Java-side setPosition and any other @CriticalNative.
