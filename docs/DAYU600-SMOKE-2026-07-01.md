## Results

Both `dalvikvm -help` commands succeeded on the DAYU600 board. This proves the staged AArch64 runtime binaries can execute on the stock uis7885 OpenHarmony userspace from `/data/local/tmp`.

The OHOS ARM64 runtime starts but times out before Java `main`:

```text
[RT] Runtime::Start() ENTERED
[icu_jni] NativeConverter registration done
[RT]   Loaded libicu_jni.so OK
[RT]   Loaded libjavacore.so OK
nullptr E ... java_vm_ext.cc:1068] Unexpected exception:
```

The bionic ARM64 runtime reaches a deeper point:

```text
[RT] Runtime::Start() ENTERED
[RT] InitNativeMethods done
[RT] JIT created successfully
[dalvikvm] Looking for class 'DynTest'
nullptr W ... Tolerating clinit failure for Ljava/io/File;: java.lang.StackOverflowError: stack size 8188KB
  at boolean java.lang.reflect.Field.isSynthetic() (Field.java:138)
```

## Interpretation

The bionic ARM64 build is currently the better DAYU600 bringup candidate despite the target being OpenHarmony/musl: it reaches runtime startup, native stub initialization, JIT creation, and class lookup before failing in a known Java/reflection initialization path.

The immediate failure to debug is not USB, flashing, fastboot, or appspawn. It is ART/core-library compatibility:

- OHOS build: `java_vm_ext.cc:1068 Unexpected exception` after `libopenjdk` native registration.
- Bionic build: `java.io.File.<clinit>` stack overflow through repeated `Field.isSynthetic()`.

## Candidate Fix

The first candidate fix makes `java.lang.reflect.Field.isSynthetic()Z` side-effect free:

- `Runtime::Start()` rewrites `Field.isSynthetic()` to a native stub.
- `UnstartedRuntime::Jni()` gets a fallback handler for the same method.
- Both paths return the `ACC_SYNTHETIC` bit (`0x1000`) from the backing `ArtField`.

This is intended to cut the observed recursion:

```text
java.io.File.<clinit>
  -> java.lang.reflect.Field.isSynthetic()
  -> java.lang.reflect.Field.isSynthetic()
  -> StackOverflowError
```

The patch has been checked with `git apply --check` against a clean `A2OH/art-latest` clone. It has not yet been rebuilt into a new DAYU600-tested `dalvikvm` because this Windows/WSL machine is missing the AOSP/OHOS paths hard-coded by the current A2OH makefiles:
