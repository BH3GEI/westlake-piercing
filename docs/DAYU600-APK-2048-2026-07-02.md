- no `dayu600-game-overlay-stub` by default;
- the stock APK's `MainActivity`, `com.digiplex.game.c` game model, touch

Two DAYU600 standalone ART issues were isolated:

- app/classpath custom `android.view.View` subclasses fail class initialization
  with exact `LinkageError`; moving `CustomButton` into the framework shim
  makes it initialize and construct successfully;
- `String.valueOf(int)` / `Integer.toString(int)` tripped
  `java.lang.ArrayStoreException` through the standalone `StringFactory` path.
  The active ART adds a narrow primitive-string intrinsic in
  `interpreter_common.cc`, and includes `stringfactory.jar` first on the
  bootclasspath.

The stock `onCreate(Bundle)` path now returns `RC:0` in the real APK route.
`onCreateManual` remains a useful stepped lifecycle marker.

## Important Limit

This is not a launcher-visible Android UI yet.

The current AppSpawnX experiment now runs the real APK probe inside the OHOS app
child, but it still uses the DAYU600 framework shim rather than the full
Westlake Android framework/adapter stack. The visible window is still created by
the stock OHOS shell, so Android `ViewRoot` / `Surface` rendering is not yet
attached to that window.

## Why It Is Not Visible Yet

The live DAYU600 board still lacks the Westlake system adapter:

```text
/system/android: absent
/system/bin/appspawn-x: absent
/system/android/lib64: absent
/system/android/framework: absent
```

The bundle is currently registered manually enough for:

```text
bm dump -n com.digiplex.game
bundleType: 10
codePath: /data/app/el1/bundle/public/com.digiplex.game/android
base.apk md5: 4104719da9affd4c5c06d791c554158e
```

The OHOS launcher shows a `com.digipl...` icon, and `aa start` can create a
stock OHOS mission, but the visible window is still an OHOS shell/blank route
because the full Android adapter is missing. The current logs also show
`entry.hap` is absent, so launcher resources should be fixed separately once a
DAYU600 `restool` is available.

The next visible-app milestone remains an aarch64 `appspawn-x`/adapter port with
the Android framework/runtime, bridge libraries, `libhwui`, and bootclasspath
artifacts rebuilt or recovered for DAYU600. It is not a fastboot, flashing, or
APK packaging problem.

## 2026-07-03 Harness Update

The temporary AppSpawnX hook no longer starts a background thread to load the
heavy WMS bridge. Heavy bridge loading is now controlled from the embedded ART
probe with:

```text
WESTLAKE_LOAD_HEAVY_BRIDGE=1
WESTLAKE_HEAVY_BRIDGE_TIMING=beforeStage|afterStage
```

This keeps the appspawn child birth path stable and makes bridge loading a
deliberate child-stage action. The default staging route still leaves it off
until the real Android framework/runtime path is ready.

DAYU600 local substrate staging now lives at:

```text
ports/dayu600/out/substrate/manifest.json
```

That manifest intentionally distinguishes the current headless probe artifacts
from the missing real adapter artifacts needed for visible Android UI.
