一页结论

早期技术判断：当前 CardWords 四个 ARM64 DSO 中已识别出的 Unity TP-relative 行为是确定性的 stack-guard 型读取，技术上可解；但轻量 TLS aperture 是否可用，仍取决于目标 Musl 对 TP+0x28..0x2f 的全生命周期非重叠证明。证明失败时必须升级到独立 Bionic TLS island、DBT，或拒绝该 generation，不能继续试写 Musl TCB。
不是随机问题机器码可静态枚举，动态代码可由装载与可执行映射门控。
不是函数替换内联读取没有 PLT/GOT 或统一调用边界，不能等发生后再 hook。
不是安装时写 TLS安装只分析和签证；TLS 必须在每次进程、每个线程存在后建立。

产品边界

保持不变西湖新增能力明确不做
APK 签名与字节；Unity DSO；真实 stack protector fatal 语义 安装认证、目标 generation 证书、运行期 entry gate、per-thread aperture、撤销审计 修改 Unity/Musl 内部；扩大符号 shim；零 guard；忽略 mismatch；未认证可执行代码

核心不变量：第一条 guest 指令之前 READY

任何线程执行第一条 Unity/Bionic 指令之前，该线程所需的兼容状态必须已经完整写入，并以正确内存序发布。
ExecuteGuestInstruction(thread, generation) => CertificateValid(generation) && ProcessGuardReady(generation, epoch) && ThreadApertureReady(thread, generation, epoch)
ArtifactAPK / DSO 精确身份
TargetOH / Musl / Loader 同代
ProcessGuard value 已发布
ThreadAperture slot 已发布

第一条访问可能在 DSO constructor、线程 start routine 的函数序言，或异步 signal handler 中发生。此时尚无可依赖的普通函数边界，所以“先运行、看到访问后再补”在构造上不成立。

01

安装 / 认证：Native ABI Admission Center

把未知二进制变成绑定具体 generation 的可执行裁决

进入条件
原始 APK、签名摘要、全部 native payload；精确 OH/Musl/loader/kernel/adapter 目标清单。
唯一 owner
西湖 Native ABI Admission Center；安装器只消费签名结果，不自行猜测兼容性。
核心动作
冻结身份 → 递归 DSO 闭包 → 扫描 TP/原子/syscall/sysreg/PT_TLS → 恢复语义 → 对拍目标布局 → 选机制 → 签证。
阶段产物
签名兼容证书、inline ledger、DSO/Build-ID manifest、target generation、机制与拒绝原因。
失败行为
QUARANTINE / REJECT；任何 UNKNOWN、目标不明或 overlap 未证明都不得进入运行期。

扫描闭包

Freeze APK + signature + every DSO SHA-256 / Build-ID
  → close recursive DT_NEEDED and provider identity
  → enumerate PT_TLS / TLS relocations / executable segments
  → scan TPIDR_EL0 and TP-derived load/store/atomic sequences
  → scan direct svc, sysregs, opaque-object atomics and generated code policy
  → classify offset / width / read-write / semantic / thread role
  → audit exact target Musl source/binary: every read/write to the candidate range
  → prove owner across initial TLS, dlopen TLS, thread, fork, signal and destructor
  → APERTURE | TLS_ISLAND | DBT | RIGHTS_GATED | REJECT
  → sign certificate

证书必须绑定的身份

  • APK SHA-256、签名证书摘要、package、ABI。
  • 每个 DSO 的路径、SHA-256、Build-ID、GNU properties。
  • 递归 DT_NEEDED 与唯一 provider。
  • OH build、Musl/loader SHA 与 Build-ID、kernel generation。
  • adapter generation 与 compatibility profile。
  • 动态代码政策、线程入口合同、证据摘要、撤销序号。

证书信任与离线撤销

  • 签发私钥由受控构建/签证服务保管；设备 trust store 只固定公钥与允许的 certificate schema。
  • 证书携带单调递增 policy_epoch、签发/到期时间、target fingerprint 与撤销序号；不得只依赖“签名数学有效”。
  • AppSpawn 每次 fork 都核对本机最低允许 policy epoch、证书时效与精确 target fingerprint。target 任一字节变化，即使未联网，也会本地失配。
  • 离线设备只允许在受控短有效期内使用已 stapled 的撤销状态；超过最大离线时限即 fail closed，不以可用性为由继续放行。
停止线：“当前字节看起来未使用”不是地址所有权证明。必须覆盖 initial/static TLS、后续 dlopen TLS、线程创建/复用/退出、fork、signal、TLS destructor 与 Musl 运行期写。若 exact Musl 把该范围用于 dtv、self 或其他活跃字段，这是结构性冲突：立即淘汰 APERTURE_NATIVE；只有独立 TLS island/DBT 的边界也能闭合时才升级，否则拒绝该 generation。
02

AppSpawn 启动：主线程 aperture

每次 fork 都创建新的运行期 epoch；安装证书不能替代线程初始化

进入条件
appspawn child 已 fork；证书和当前 target generation 可验证；尚未加载或执行 guest constructor。
唯一 owner
appspawn-x child 中的 native compatibility gate / app-native-loader 前置门。
核心动作
重置 child-local epoch → 验证证书 → 建立 process guard → 发布 PROCESS_READY → 写主线程 slot → 发布 THREAD_READY。
阶段产物
主线程 READY(generation, epoch)；结构化启动审计记录。
失败行为
在 dlopen 前终止 native load；不得默认成功、不得执行 constructor。
fork child
  → reset inherited locks, registries and child epoch
  → verify certificate + APK/DSO/target/adapter identity
  → prove no guest instruction has executed
  → compute and write process guard value
  → release-publish PROCESS_READY
  → acquire PROCESS_READY; write main-thread aperture slot
  → release-publish THREAD_READY
  → only now: map guest DSO → constructors → JNI_OnLoad
  • PrepareCurrentThreadAperture() 自身必须是 Musl-compatible host 代码，不能依赖 guest stack guard。
  • 必须早于 dlopen，因为 constructor 在 dlopen 返回前执行。
  • fork 后 guard 是继承还是重播种，只能由目标 Bionic oracle 决定。
  • parent appspawn 不得预执行 app-private Unity constructor。
03

Unity 线程创建：唯一 pthread broker

不是拦截线程里的每次读取，而是在 start routine 第一条 guest 指令前准备一次

进入条件
静态 DSO 与所有允许的动态代码闭包成立；Unity 可见的 pthread_create 全部解析到唯一受控 provider；证书声明该线程角色可准备。
唯一 owner
L03.A15 pthread broker + host trampoline。
核心动作
创建前由 broker 屏蔽 guest signal → 子线程从内核原子继承掩码 → 准备 slot → 二次核对 process token → 发布 READY → 才调用 Unity start routine。
阶段产物
每线程 generation/epoch/role 状态、entry/exit/destructor 计数。
失败行为
不调用 guest start routine；标记 QUARANTINED。直接 clone 绕过无法闭合则撤销 aperture profile。
Unity pthread_create(..., guest_start, arg)
  → validate attributes + start pointer ownership
  → broker blocks the certified guest-signal set before pthread_create
  → create host/Musl thread with host_trampoline
  → child atomically inherits blocked mask; parent restores its old mask
  → child acquires PROCESS_READY(generation, epoch, policy_epoch)
  → write this thread's certified aperture slot
  → re-read process token; any change means QUARANTINED
  → CAS PREPARING → THREAD_READY with the same token
  → unmask allowed guest signals
  → branch to guest_start(arg)

退出与复用

  • 先禁止新 callback，再完成 guest TLS destructor 合同并标记 RETIRED(epoch)。
  • 只有 callback/signal 引用为零时，才能释放 side metadata。
  • 线程池复用必须核对 generation/epoch；退休状态不得被继承为 READY。
  • 认证发现 direct clone/clone3 或直接 syscall 绕过 broker 时，必须纳入受控 child trampoline、升级 DBT/island，或拒绝。
  • 若存在不可枚举的 JIT、自修改代码或 executable mapping，所谓“唯一 broker”证明立即失效，必须转入动态代码门或拒绝，不能只依赖静态扫描。
04

OH / Musl 回调：Typed Callback Gate

任意 host 线程进入 Unity 前，先证明它属于同一证书 generation 与 epoch

进入条件
guest function pointer 在注册时已绑定 owner、签名、generation、epoch 和生命周期。
唯一 owner
每个跨界 bridge 的 typed callback trampoline，统一遵守 L03.A15 guest-entry contract。
核心动作
host trampoline 查 registry → 验 process/thread token → READY 快路径；仅在尚未解引用/调用 guest pointer 且满足可准备合同的 HOST_ONLY 线程上执行受控准备 → 二次核对 token → 进入 guest。
阶段产物
callback registry、entry depth、miss/reject counters 与可追溯 owner。
失败行为
fail closed；raw guest pointer 逃逸使 missing_thread_entry_count 非零并撤销证书。
OH callback arrives on thread T
  → execution is still inside a Musl-compatible host trampoline
  → block certified guest signals; do not dereference/call guest code
  → verify callback registry + owner + generation
  → inspect T aperture state
  → READY for same epoch ? O(1) fast path
  → HOST_ONLY and certificate says PREPARABLE ? CAS to PREPARING
  → prepare slot; revalidate process token; publish THREAD_READY
  → otherwise reject
  → increment nested guest-entry depth
  → invoke Unity callback
  → decrement depth; restore host boundary state
这里不是“发生内联后再补”：允许准备的唯一位置是尚未执行、解引用或调用任何 guest 地址的 host trampoline，并且使用与 pthread broker 相同的 PREPARING/CAS、signal mask、token 二次核对和 release-publish 协议。signal handler、loader/allocator lock 持有期间、raw guest pointer 路径、已进入 guest prologue 后，或线程地址布局不满足证书时，一律不能准备。
05

实际内联访问：直接读取，不再拦截

性能收益来自把确定性工作前移到认证与线程入口，而不是让每次读取过 helper

进入条件
证书有效；process/thread READY；当前代码页属于证书闭包；generation/epoch 一致。
唯一 owner
原始 Unity/Bionic 机器码；运行期 auditor 仅观察边界计数，不改写每次访问。
核心动作
原样执行 MRS TPIDR_EL0 与固定偏移 load；stack protector 正常比较 guard。
阶段产物
原生访问性能；真实 mismatch 仍进入 __stack_chk_fail。
失败行为
guard/canary mismatch 保留 fatal 语义并采证；禁止零值、固定常量或屏蔽失败。
mrs x20, TPIDR_EL0
ldr x8, [x20, #0x28]

No function hook
No GOT / PLT lookup
No helper call per access
No page-fault lazy initialization
No Unity binary patch

Aperture 成功时，每次内联读取与原 Android ARM64 机器码等价，新增成本集中在每进程、每线程和 callback 边界。它仍只解决证书声明的 TLS 行为，不自动解决 pthread 对象快路径、signal frame 或 C++ unwind ABI。

异步闭包：signal 与 post-fork

Signal

slot written
  → THREAD_READY published
  → guest-owned signal unmasked
  → handler may execute
  • PREPARING 期间屏蔽 guest-owned signal。
  • process-directed signal 只投递到 READY 线程，或经唯一 signal broker 转发。
  • handler 只能读取预发布状态，不 malloc、加锁、dlopen 或初始化。
  • altstack、ucontext、sigset 是独立 signal ABI 合同。

post-fork

  • child 创建新 epoch，清理继承锁、registry 与线程状态。
  • guard 继承/重播种由 exact Bionic oracle 决定。
  • 重新发布 PROCESS/THREAD READY 前禁止 guest 执行。
  • parent/child 证据按 PID、boot、generation 分开记录。
关键风险：继承到 child 的“看似 READY”状态不能自动代表 fork 后状态完整。

游戏内刷新 `.so`：可处理，但必须先认证后执行

普通 loader 可见路径有机会统一管控；绕过 loader 的 executable mapping 则需要更低层的映射门、DBT 或拒绝。产品默认采用新进程 generation，不做未经证明的进程内热换。

download / update
  → non-executable quarantine
  → open exact file; hash / signature / fstat
  → recursively close DT_NEEDED + PT_TLS
  → scan inline ABI and recompute aperture overlap
  → issue incremental certificate
  → promote and load the same immutable / sealed FD
  → restart into a new process generation
  → verify again before mapping and constructor
加载路径普通 loader gate产品处理
ClassLoader / NativeLoader可管控统一 backend，核对 namespace、证书、same-FD。
dlopen / nested dlopen有条件可管控app namespace 只能解析到唯一受控 provider。
android_dlopen_ext / FD load有条件可管控验证并加载同一个 sealed FD，禁止重新按 path 解析。
DT_NEEDED可管控root constructor 前闭合全部递归依赖。
memfd + executable mapping不充分sealed FD + executable-map gate；否则拒绝。
mmap/mprotect(PROT_EXEC)不可仅靠 loaderkernel/SELinux/LSM 或 mapping broker；否则拒绝。
direct svc / JIT / self-modifying不可见DBT、专用 JIT policy + W^X + attestation，或拒绝。

即使新 DSO 自身没有 TP 读取，只要它带 PT_TLS 或改变 loader TLS 分配，旧 aperture 非重叠证明也可能失效，必须重新计算并撤销旧证书。

解决机制字典与升级路线

裁决码适用条件访问成本改二进制 / 权利风险停止条件
APERTURE_NATIVE固定 slot；exact Musl 全读写点已审计；目标地址所有权和永久非重叠已证明；入口全闭合。内联热路径 P0不改 APK/DSO活跃 Musl 字段、任何 overlap、unknown 或 entry miss 都立即淘汰此机制

“技术上可解”与“当前产品路线可接受”是两件事。性能、系统权限、二进制变更和权利门必须独立记录，不能把高成本或未授权简化成抽象的“无解”。

并发状态机与正确发布顺序

Process

UNINITIALIZED
  → INITIALIZING
  → READY(generation, epoch, policy_epoch, guard)
  → RETIRING → RETIRED

any error → FAILED

Thread

HOST_ONLY
  → PREPARING
  → READY(generation, epoch, policy_epoch)
  → IN_GUEST(depth ≥ 1)
  → READY → RETIRED

any error → QUARANTINED

修复历史 A07 的 TOCTOU

禁止顺序本设计顺序
ready=1 → write guard；读者可能在窗口内读到 0/旧值。 compute/validate → write guard → release PROCESS_READY → acquire → write slot → release THREAD_READY → acquire 后进 guest。

防止 generation / epoch ABA

  1. generation + epoch + policy_epoch 组成单调 process token；同一 token 不复用。
  2. 线程从 PROCESS_READY acquire token，写 slot 后必须再次 acquire process state；token 或 READY 状态变化即进入 QUARANTINED。
  3. 只有以同一 token 完成 CAS(PREPARING → THREAD_READY) 才可发布；callback gate 在调用 guest 前再次同时核对 process/thread token。
  4. Process 进入 RETIRING 时先关闭新 entry，原子阻止 PREPARING 线程继续发布，等待 IN_GUEST/entry lease 排空后才退休旧 generation。

ARM64 弱内存序必须由 target litmus/stress 证明；x86 host 或 QEMU PASS 不能替代真机 acquire/release 证据。

验证阶梯与 PASS 合同

  1. Host/static：双扫描器站点集合一致，unknown 为 0；证书 mutation、target mismatch、duplicate provider、unknown DSO 全部 fail closed。
  2. Target minimal fixture：constructor-first、main、new thread、callback、pool、post-fork、signal 六入口；PT_TLS 动态 DSO 正负控；canary 与弱内存序 stress。
  3. Unity device gate：exact APK/DSO/target manifest，production listener，Enforcing，reboot + NO_JIT 第一个 truly-cold child，两个不同 boot ID。
  4. 后续楼层：TLS PASS 只允许进入 signal ABI → EGL/Surface → 首帧，不得冒充 Unity 已上屏。

当前证据状态：不把设计写成实现

Proven · host/static

  • TP 之外的 direct syscall、opaque atomics、signal/JIT 全量 ABI 闭包。
