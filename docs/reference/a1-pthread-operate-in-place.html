A1 方法：operate-in-place pthread 翻译 —— 前因、后果与适用场景

A1 是"不改字节、原地翻译"的 bionic↔musl 线程同步方案：让 musl 进程按 bionic 协议直接操作 bionic 布局的 mutex/cond/rwlock 对象。本文梳理它为什么存在（前因）、做到了什么、边界在哪（后果），以及什么时候该用、什么时候不必用（适用场景）。

前因为什么需要 A1 —— "内联访问"死结

Unity 的 libunity 把 pthread mutex 的 fast-path 内联进了引擎代码，绕过符号；而 bionic 与 musl 的锁对象字节布局根本不同。两条常规路都是死路。

根因bionic 与 musl 的锁字不在同一个地方

bionic 的 mutex/cond 把 futex 字放在 offset 0；设备 musl 的锁字 _m_lock 在 offset 4、_c_seq 在 offset 8，而 offset 0 在 musl 是 _m_type/_c_shared（不是锁字）。编码不兼容、协议也不同（musl cond 用 barrier + FUTEX_REQUEUE）。

把 bionic 字节裸喂给 musl → 锁字读错位 → lost-wakeup 永久死等。这正是变体3 里 pthread_cond_timedwait 在 gfx-init 挂死的字节级根因。

死结两条常规路都不通

路 A · Boxing（换字节，把 bionic 对象翻译成 musl 布局）
↓ 破坏 libunity 内联 fast-path（log-sink 内联 mutex，x0=1 崩）
路 B · 不翻译（裸喂 bionic 字节给 musl）
↓ 锁字错位 → lost-wakeup 死等
A1 · operate-in-place（字节不变，按 bionic 协议原地碰同一 state 字）

核心矛盾：libunity 内联了 fast-path，无法靠拦截符号解决——因为内联根本不走符号。任何"换字节"的方案都会和内联的那一份实现打架。

方法operate-in-place —— 不换字节，按 bionic 协议原地碰同一 futex 字

A1 的立论：只要字节布局不变，libunity 的内联 fast-path 与 A1 的 shim 就操作同一个 state 字、遵同一协议 → 天然一致，不需要拦符号，任何未修改 app 都受益。

  • 字节不变 + 裸 futex：shim 对 bionic 布局对象用同一 bionic 协议 + 裸 futex 系统调用（__NR_futex=98）原地操作同一 state 字。inline ↔ shim 因此一致，无需符号拦截。
  • 三原语全量：mutex（NORMAL/RECURSIVE/ERRORCHECK/trylock/timedlock）+ cond（V11 无 REQUEUE、always-wake）+ rwlock（writer/reader-pref，含 FIX-1/2/3）。
  • 逐字锚定 AOSP-V11 bionic：布局 mutex 40B / cond 48B / rwlock 56B，编译期 _Static_assert + 运行期 dump_layout 双重自证与真机对齐。
  • cond 关键洞见：Android 11 的 cond_wait 没有 REQUEUE（之前担心的最难点不存在）——只是 snapshot → unlock → FUTEX_WAIT_BITSET → relock；且 V11 无 waiters 字段，shim 必须默认 always-wake，否则读脏 waiters 漏 WAKE。
  • de-macro 双实现（防伪 PASS 的关键设计）：bref_*（独立手写逐字移植 AOSP-V11 cpp，既是 oracle 又代表 libunity 内联）与 a1_*（走 GEN_ 宏的 shim）是两份真正独立的实现，对同一对象混跑 = 真差分（要复现转写 bug 得两处各犯一次）。
一句话 因为不碰字节，内联的那份实现和 shim 天然自洽——这就是"内联访问"问题的通用解，也是它能对任意 unmodified app 生效的原因。

场景什么时候该用 A1 —— 以及为什么当前不必用

A1 是有价值的通用基建，但 5-codex 审稿团的战略裁决很明确：它不是 Unity 上屏的钥匙。分清这两点能避免在非关键路径上过度投入。

✓ 适用A1 该出场的场景

  • 某个 bionic 编译的 app 跑在 musl OS 上，需要 pthread 对象跨边界正确互操作；
  • 并且存在"内联访问"问题（锁 fast-path 被内联，拦不到符号）；
  • 并且多线程正确性要紧（job system、多 worker、生产者-消费者紧握手）——弱序机器上正是踩坑高发区；
  • 定位 = 通用 bionic-on-musl「已知正确」sync 基建，字节不变故任何 unmodified app 受益。

✗ 不必当前 Unity 上屏为什么不用 A1

  • cardwords 上屏全程零使用 A1：真墙全在数据/图形/音频/几何，不在 libunity pthread ABI 深水。当前栈不 box libunity 锁，内联 fast-path 自洽休眠即可。
  • 真墙 = missed-wakeup（GfxDeviceWorker 从 never spawn）——即便 A1 完美，唤醒没有来源，上屏收益为零。上屏关键路径是 cond_wait interpose 追的 missed-wakeup，不是 cond-ABI。
  • 已验证的负结果：force-gfx-direct / threading-mode patch 同样证伪（真墙在上游）。工厂不必为每个 app 做 libunity 锁翻译。
★ 多 codex 审稿最大价值 诚实指出 A1 技术严谨但不是上屏 blocker，防止在非关键路径上过度投入。A1 的正确身份是 M1 能力模块——第一个走完「UT + 真机 AT」的样板与守护化通用基建（默认 V11、禁未验证 waiters 短路），备用不启用于当前上屏栈。
