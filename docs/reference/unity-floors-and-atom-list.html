两套坐标系是同一份工作的两个视角。 B4（Unity 能力原子）≡ L01–L06 里的 G/A/Q；底座类 F1–F5 分散在 B2/B3/B5。上屏用 L 视角看得清（引擎穿透的墙序），复现用 B 视角看得清（从 clean 源的构建依赖序）。当前状态：cardwords（Unity 2022.3.62f2）在 D600 两台设备实测 ≈59.9fps 冷启动零崩。

四、测试完善清单 为让"各种 Unity 游戏"都跑得理想 · 按优先级

当前全部验证建立在 单一游戏 cardwords（竖屏 1080×1920）之上。从"一个游戏 60fps"到"各种游戏理想"，缺口不在已破的墙，而在泛化覆盖——参数化、多分辨率、多线程压力、跨引擎、跨部署路径。下列按风险排序。

P1

Q2 buffer 几何 — 多分辨率 / 多方向参数化

L05.A02 · B4.A05

兜底值是硬编码 1200×1920，只对 cardwords 竖屏成立。GAME1 是横屏 1920×1080，own-staging 路径下几何链行为已不同。任何非此分辨率/方向的游戏都会拿到错误 swapchain 尺寸 → 拉伸、黑边或 0 帧。

测什么：竖屏/横屏 × 常见分辨率（1080p/1200p/2K/异形屏）矩阵；正解方向是 mint 处加 SET_BUFFER_GEOMETRY 参数化（从窗口真实尺寸派生），替换硬编码，再跑矩阵回归。

状态 = BLOCK · 阻塞可玩态泛化
P1

GC Finalizer — 长时稳定性 + 根治替代

L02.A02 · F4

GC_DONT_GC=1 是绕过而非根治：全禁 GC collection 会导致内存无界泄漏。短会话 demo 无碍，但真实游戏长时间玩下去会 OOM。根因是 Boehm GC × musl 的 setjmp 栈扫描不兼容。

测什么：长时（30min+）内存曲线压测判 OOM 边界；验证更干净的 GC_DISABLE_INCREMENTAL=1（保留 GC 只禁 musl 不兼容的增量 write-barrier）是否可替代；对内存密集型游戏尤其关键。

绕过非根治 · 内存泄漏风险
P1

pthread box — 真机弱内存序（G7）

B2.A01 · A1 基建

pthread/mutex/cond boxing 在 QEMU aarch64 判 SOUND（9/9 绿），但负控第 5 例 neg_mtx_relaxed 被 QEMU 的 TSO 强序掩盖——真实 ARM 弱序机器上的内存序回归尚未验证。多线程 Unity 游戏（job system、多 worker）正是弱序踩坑高发区。

测什么：真机 G7 弱序压测（device_g7_run.sh 就绪待放行）；高并发 mutex/cond 混用、broadcast 栅栏、生产者-消费者在真机上跑到 1e6+ 迭代验无丢唤醒/无序违例。

QEMU 掩盖弱序 · 多线程游戏高发
P2

B4 全部能力 shim — 跨游戏泛化矩阵

B4 全层 · L04/L06

swappy_kill / egl_damage / geomfix / unity_bridge / font_prime 全部只在 cardwords 一个游戏验证过。GLES3 派发（G2）只补齐了 cardwords 用到的 proc 子集；FMOD stub（A1）只覆盖 FMOD 触碰的 16 个 native。

测什么：建游戏矩阵（HelloWorld / noice / 重图形 / 3D / URP / 不同 Unity 版本）逐一冷启动跑通；重图形游戏会命中更多 GLES3 扩展枚举 / compute / vulkan 路径；不同音频引擎（Wwise / 原生 AudioTrack）会命中 A1 未覆盖的 native。

单游戏验证 · N-app 复用未验
P2

跨部署路径 — GAME1 own-staging 5 墙

B3 + B5 部署链

自编游戏走独立部署路径（route3 壳 + own-staging）级联撞出 5 面墙，前 4 已修、第 5 待修——这些正是"各种游戏各自装"会遇到的泛化缺陷：①aapt2 资源包名错配 ②il2cpp bind 目标不存在（overlayfs 修）③input-bridge NSME runtime 版本敏感 ④HWUI Minikin 字体 reprime 时序 ⑤RS 事务并发崩（待修，native present-wall）。

测什么：把这 4 个普适修法（资源包名 / overlayfs / 47bb82aa runtime / child reprime）纳入安装期标准流程并对新包回归；第 5 墙 RS flush 串行化需恢复 sysroot 构建后验证。

部署路径泛化 · 第 5 墙 native 待修
P2

FGGUARD grace 窗口 — 首帧时长分布

L02.A03 · B3.A06

FGGUARD 的 grace 默认 3s——重游戏（大 il2cpp、多资源）首帧可能超过 3s，导致伪 STOPPED 未被吞掉、引擎仍被 pause 打断。

测什么：采集不同游戏的首帧时长分布，确认 3s 覆盖长尾；必要时把 OH_FGGUARD_INIT_GRACE_MS 按包大小/首帧预算参数化。

重游戏首帧长尾
P3

L07 HWC 直通 — overlay 直扫 + composer 补丁验证

L07.A01 / A03 / A04

功耗优化层（非上屏必需）：RS 侧已达 6% CPU，但硬件 DPU overlay plane 直扫（A01）、UNISOC composer 字节补丁（A03）、Unity 整合验收（A04）都待真机验证。

测什么：A01 最小 DRM 测试确认非 primary plane 可扫；A03 按 L0→L3 安全阶梯逐级 truly-cold 验（先只改 P2 supportLayers）；A04 整合后 render_service <10% 且仍 60fps。每级需 restore 可回滚。

功耗优化 · 硬件路径待验
P3

Q1 present-XCOM — 多窗口 / 旋转 / 弹窗场景

L05.A01 · B3.A05

present-XCOM 在单一全屏静态场景验过；多 window、运行时旋转、系统弹窗抢前台、split-screen 等场景的 Z-order / surface 交接未系统覆盖。

测什么：旋转 / 弹窗 / 后台-前台往返 / 多 Activity 切换下的 present 正确性与无并发崩（与 GAME1 第 5 墙 RS 并发同源，建议合并验）。

复杂窗口场景未覆盖
已验证的"不需要"（负结果，省测试力气）： libunity pthread 锁 boxing / 内联访问（cardwords 全程零使用，真墙全在数据/图形/音频/几何，不在 libunity pthread 深水）· force-gfx-direct / threading-mode patch（证伪，真墙在上游）。这三项不必为每个游戏投入测试。
