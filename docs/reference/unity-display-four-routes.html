03

最小分歧层判定

L05.A12 + L03/L04 L4差异应止于 L5 引擎二进制，其余皆"接缝泄漏"

对齐大表读出的铁结论：路线2(团结) 与路线3(Unity) 的分歧不在"怎么画"（L05.A06/L11 EGL/GL 两者完全相同、同 Mali），而在"谁给它窗口、经哪套 libc"：

· 窗口来源(L05.A12)：团结从自绘 RSSurfaceNode 单一所有者直取裸 OHNativeWindow*，几何在节点建立即权威单点，根本没有几何墙可撞；标准 Unity 经 SurfaceView→BLAST→AdapterAnw 双包装 → producer↔consumer 几何 split-brain = 路线3 几何墙。

· ABI 后端(L03/L04)：团结 musl-native 整条路不进 adapter(L3)+bionic-compat(L4)；路线3 bionic 必被 adapter 托管，每道 bionic→musl 翻译都是潜在墙（Mali 0x10000000f / GC setjmp / hwui 截断皆此类接缝泄漏）。

设计纪律（/opt/21.Game/团结vs变体3 元结论）：团结↔Unity 的全部差异应止于 L5 引擎二进制（musl-native vs bionic 两种编译目标）；路线3 其余各层的专有墙都是"接缝泄漏"，团结那一侧就是"本该长什么样"的 oracle。

对路线3 的直接启示换"窗口来源"，别在包装的 BLAST 上跟权威死磕

路线2 已把正解证在设备上：让路线3 的桥把引擎拿到的 window 换成与团结完全相同的自绘子 RSSurfaceNode（isWindow=false + SetHardwareEnabled(XCOM) + AddChild），即 bridge 已有的 oh_rs_get_child_surface_window(L931，c080a559)。producer=consumer 单一所有者→几何单点、无 split-brain、无 wrap/解包/churn。独立佐证：同一自绘路的 S21 修(桥 e5399aad) truly-cold 实证 NO_BUFFER→0 / Buffer[0 0]→0 / EGL_BAD_ACCESS→0，且 eglprobe 曾打到全屏红像素。

与当前 cut6 的关系：cut6 的 in-process BufferQueue 换面已破 alloc（治权威分裂的标），换 SOURCE 是从一开始不制造分裂（更根本）；二者殊途同归到"consumer 几何权威"。当前卡 Mali=下游墙、换 SOURCE 也要过，故先按 L4 接缝泄漏攻 Mali，不为纯洁性回退 cut6。

04

Unity 战略选择：应走哪条路

目标是运行未改的（乃至下载来的）标准 Unity 安卓 APK——只有路线3 能做到；路线2 证明机制可行、并充当逐层 oracle。

推荐

走路线3（标准 Unity 经 adapter），以路线2 为逐层 oracle

通用透明 · cut6 已破最硬的几何墙
优点
  • 通用：跑任意未改 Unity APK（符合 /goal）
  • 透明：不需用团结重编游戏
  • cut6 已破几何，仅剩 Mali 等接缝泄漏
  • 团结(路线2)是每层干净 oracle，逐墙有本可对
缺点
  • L4 bionic-compat 每边界=潜在墙（Mali/GC/hwui 截断）
  • 比原生慢、工程量大
  • 墙会继续下移，需逐一对 oracle 修
✅ 首选：唯一满足"跑标准 Unity APK"目标者；用路线2 去风险，把差异逼回 L5 引擎二进制

退路：路线2（团结引擎）

已 device-proven 60FPS，但改变前提
优点
  • 已跑通 60FPS，无接缝泄漏
  • musl 原生、干净、高性能
缺点
  • 要求游戏用团结引擎重编，不适用任意/下载的 Unity APK
  • 非透明桥，不满足"跑标准 APK"目标
  • 路线1（纯原生）更甚：需完整原生 port，非 APK 路
⚠️ 仅当可控制游戏源码/接受团结重编时采用；否则作 oracle 与去风险参照，不作交付路径

一句话战略

Unity 走路线3，把路线2 当 oracle。路线3 是唯一能跑未改标准 Unity APK 的路（=项目目标）；路线2(团结)证明了 OH 上屏机制正确、并为路线3 每一道下移的墙（几何✅→Mali→GC→hwui）提供"本该长什么样"的干净对照。cut6 已破最硬的几何墙，把路线3 与路线2 的真实差异逼近到只剩 L4/L5 接缝泄漏——逐一照 oracle 修平，即达"差异止于 L5 引擎二进制"的设计终态。
