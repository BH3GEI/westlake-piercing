§2 引擎-init · Phase C（活跃前沿）

Unity 在 UnityMain（native attach 线程）上初始化时，反复经 JNI 回调 Java 边界拿 Context / 包信息 / asset-pack 路径。这一段的原子墙全是"边界返回 null / 畸形串，Unity 不 null-check 就用"——治本在适配层把边界喂对，而非改 ART。

C1Context receiver 接线攻关中
症状UnityMain 崩于 musl strlen(NULL)：Context.getPackageName()（jmethodID holder+0x670）返 null jstring → Unity 生产者 sub_c44e4c 置 String.data=NULL 不检查即 strlen
根因非 ContextImpl 主体（适配层 OhApplicationInfoConverter:56 已设 packageName，空也是 ""→strlen 0 不崩）。强推断 = receiver（Unity 缓存的 Context/Activity jobject，.bss 0xe3c140）在 UnityMain 线程为 NULL → 传 NULL 给 CallObjectMethod → ART 返 null jstring。解释"主线程 onResume 正常、native 线程崩"
修法治本：activity 桥修 UnityMain 缓存的"当前 Activity"接线（AbilitySchedulerBridge / LifecycleAdapter handleLaunchActivity + UnityPlayer 构造时序）令 receiver 非 NULL。兜底（铁律3合规）：JNI 边界把 Context String getter 的 null 归一化为真包名/真 apk 路径
验收strlen(NULL) 过；getPackageName 返合法串
现状strlen band-aid 临时过（设备确证 wall1，child 过 onResume→foregrounded）；真修 = bridge JNIEnv CallObjectMethodV null-receiver 归一化（需 bridge 重编，native 深水待做）
依赖← B5
弹药unity_assetpack_boundary_RE.md（符号化铁证）
C2asset-pack / data-path 解析预测
症状同一引擎-init 函数 0x57ad20 解析 UnityDataAssetPack / UnityStreamingAssetsPack / UnityTextureCompressionsAssetPack；姊妹边界 getPackageCodePath（holder+0x650）走完全相同 null→strlen 模式
根因与 C1 同源（receiver NULL 或 apk 路径边界 null）——很可能随 C1 一并解
修法C1 的边界归一化须同时覆盖 getPackageCodePath；返真 apk 路径（非空串，否则 asset-pack 拼路径再崩）
验收asset-pack 4 串解析无 strlen 崩，data-path 有效
依赖← C1
C3GC-Finalizer pthread（翻案已破）已破
症状SIGSEGV 野 pc 0x7e10000004，曾误判为 ART entrypoint 损坏 / 铁律1 禁区
真相决定性翻案 = il2cpp 自带 Boehm GC(bdwgc) 的 "GC Finalizer" 线程：pthread_create 用 bionic-layout pthread_attr_t，在 OH-musl flat namespace 直落 musl（bionic→musl box shim 从不触发）→ 畸形子栈 → musl __clone blr 垃圾 entry-fn。非 ART、非 entrypoint、非禁区、非 strlen-shim artifact
修法AonB 修（铁律3 合规）：liboh_pthread_gotpatch.so（23f64111，GOT-patch libil2cpp 5 个 pthread 槽到 libbionic_compat box）+ GC_DONT_GC=1
验收truly-cold ×2：PTCGOT 5 槽全 patch，0 复现，Unity worker Init returned 1 连发
依赖← 独立（il2cpp 运行时）
C4JNI 边界 null 系统审计预测
症状C1/C2 是"边界返 null，Unity 不检查"这一类墙的头两个实例。libunity 缓存整张 Context / AssetManager / PackageManager 方法表，任一 getter 返 null 都同样崩
修法一次性审计 libunity 引擎-init 缓存的全部 JNI getter（Context/AssetManager/ApplicationInfo/Resources/PackageManager），在适配层统一保证非 null 非畸形返回——把"逐个崩逐个修"变成"一次覆盖"
验收引擎-init 全程无边界-null strlen/deref 崩
依赖← C1（模式确立）

§6 关键路径 · 从"上屏"到"自动测试完成"全链

两段主链：先 8 原子到 D5（截图见像素 = 上屏），再经 E + F 共 9 原子到自动化验收出报告。C4 是"把逐个崩收敛成一次覆盖"的加速器（可折叠 C2 及 D1 前的隐藏边界墙）。

B5→ C1→ C3✓→ C4→ D0★→ D1→ D2→ D3·D4→ D5 · 像素

C3（GC Finalizer 野 pc）不在主链上——它疑为 strlen band-aid 的 artifact。用 C1 治本（不注 preload）后大概率消失；只有它在治本后仍复现，才升级为独立深水原子（铁律1，落 base 最小修，不碰 vtable）。F5 回归门贯穿全链：每个原子的设备部署都先过它，不是终点才做。

§7 攻关并行性 · device-free vs 设备串行

加速的关键：能离线预构建的原子（RE / 弹药编译 / 边界审计）与只能设备串行验证的原子分离。一台 5bb5 是设备验证瓶颈；离线线可无限并行。
